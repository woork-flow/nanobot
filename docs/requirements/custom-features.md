# 定制功能需求

> 本文档描述 nanobot 的定制功能需求，与具体版本无关。
> 文档只描述「要什么」与「边界、验收」，不涉及实现方案，也不引用代码位置。
> 用途：每次升级到新版本时，对照本文档逐条核对各需求是否仍被满足；不满足则按需求重新落位。
> 整理日期：2026-09-16　修订日期：2026-09-17（按评审结论补齐歧义、边界与验收标准；原需求 1、2 合并为需求 1；需求 4 的升级迁移条目按「定制部署无存量 `AGENTS.md`」结论改为不适用）

## 核对总览

| 需求 | 一句话判据 | 与上游的关系 |
| --- | --- | --- |
| 1 | 配置可全局关闭 Dream，关闭后定时任务、手动命令、上下文注入三个面向全链路不生效 | 冲突：上游开关只作用于定时任务；其中「上下文注入」子项为条件性 |
| 2 | `/git [message]` 一键提交并同步当前会话工作区 | 新增：上游无此命令 |
| 3 | `/read <filename>` 只读工作区内的 Markdown | 新增：上游无此命令 |
| 4 | 项目指令文件名为 `NANOBOT.md` | 冲突：上游使用 `AGENTS.md` |

## 需求 1：Dream 功能的配置级开关（关闭后全链路不生效）

### 用户故事

作为部署方，我希望能够通过一个配置项全局关闭 Dream（记忆固化/整合）功能，并且关闭后 Dream 机制完全不生效：后台定时任务不运行，所有手动触发的 Dream 命令被拒绝并给出明确提示，会话上下文也不再带入与 Dream 配套的最近记忆历史。

本需求覆盖三个面向，关闭 Dream 时需同时满足：

- 面向 A：后台定时任务不注册、不运行。
- 面向 B：所有手动 Dream 命令被拒绝。
- 面向 C：不把「最近记忆历史」注入主循环上下文。

### 术语约定

- 最近记忆历史：把「尚未被 Dream 整合的近期对话内容」注入到系统提示/上下文中的机制。它与「长期记忆文件内容的注入」是两件不同的事。
- 临时会话：本轮对话不落盘、不参与记忆沉淀的会话形态（例如 Dream 自身运行、一次性/临时对话）。
- Dream 已启用：本需求的配置项取值为 `true`。

### 功能需求

1. 提供配置项 `agents.defaults.dream.enabled`（布尔，默认 `true`），控制 Dream 功能是否启用。配置名、层级与默认值需保持稳定，便于升级后核对。
2. 面向 A：当 Dream 被禁用时，后台 Dream 定时任务不注册、不运行；此前已注册的定时任务需被清除，重启后也不再出现。
3. 面向 B：当 Dream 被禁用时，所有手动 Dream 命令（`/dream`、`/dream-prompt`、`/dream-log`、`/dream-restore`）一律被拒绝，包括其中的只读查看形态（如列出历史版本、查看当前记忆指引）。不区分「查看」与「操作」，以免核对时产生歧义。拒绝后不得发起任何整合、读写或回滚动作：记忆文件、历史进度、版本记录均保持原样。
4. 面向 C：上下文构建中「注入最近记忆历史」的取值条件为：
   `注入 = (非临时会话) 且 (Dream 已启用)`
   - 即：临时会话一律不注入；非临时会话但 Dream 被禁用时也不注入。
   - 注入范围仍限定为「尚未被整合的部分」，不得把已整合过的历史重复注入。
   - 注意「临时会话」这半个条件与 Dream 开关无关，属于独立的注入前提，不因开关状态而改变。
5. 拒绝提示需满足：
   - 明确指出 Dream 已被 `agents.defaults.dream.enabled = false` 禁用，并指引在配置中开启。
   - 所有 Dream 命令使用同一套提示口径，便于逐条核对。
6. 进度语义：禁用期间新产生的对话历史，不得在重新启用后被一次性整合。即禁用时应视为「该期间历史已被跳过」，重新启用只处理启用之后的新历史，避免超长整合与记忆污染。
7. 能力边界（避免误判为回归）：
   - 禁用 Dream 不影响既有长期记忆的读取与正常注入，已有记忆仍然可用。
   - 禁用 Dream 不影响会话压缩、归档等其他记忆相关能力；压缩/归档产生的摘要注入不由面向 C 控制。
   - 面向用户的配置说明（含 WebUI 文案）需与本条一致：关闭后既有记忆仍可用，只是不再自动整理。

### 验收标准

- 面向 A：关闭后启动，不存在 Dream 定时任务，运行状态显示 Dream 已关闭。
- 面向 B：关闭后逐个执行 `/dream`、`/dream-prompt`、`/dream-log`、`/dream-restore`，均被拒绝，提示包含配置项名，且记忆文件、历史进度、版本记录无任何变化。
- 面向 C（三种组合分别验证）：
  - 临时会话：无论 Dream 开关状态如何，均不注入最近记忆历史。
  - 非临时会话 + Dream 关闭：不注入。
  - 非临时会话 + Dream 开启：注入，且只包含尚未整合的部分。
- 三种组合下，长期记忆注入与压缩/归档摘要注入行为保持不变。
- 重新开启后：Dream 恢复原有行为，且禁用期间的历史不会被一次性整合。

### 上游差异提示

- 面向 A 与 B 属于必须落位的定制：上游的该开关只控制「是否注册定时任务」，不控制手动命令。每次同步上游后需重新核对拒绝口径、提示文案、以及禁用期间的历史进度语义是否仍然成立。
- 面向 C 属于条件性需求：只在上游仍存在「最近记忆历史注入机制」时才需要落位。若上游已取消该机制（例如改为仅依赖会话摘要检查点），则面向 C 自然满足：核对时只需确认不存在这类注入即可，**不要为了「补落位」而重新引入该机制**。
- 核对时不要因为面向 C 当前处于「自然满足」状态，就把整个需求 1 判定为无需落位；面向 A、B 始终需要核对。

## 需求 2：工作区 Git 同步命令 `/git`

### 用户故事

作为用户，我希望通过 `/git [message]` 一条命令，把当前会话工作区的改动提交并同步到远程仓库（提交 → 拉取 → 推送），从而便捷地备份/共享工作区状态。

### 功能需求

1. 命令形态：`/git` 与 `/git <message>` 两种写法都需可用；命令需登记为内置命令，并出现在帮助与面向用户的命令文档中。
2. 作用范围：作用于「当前会话生效的工作区」；当会话没有独立工作区时，使用默认工作区。不得对工作区之外的目录执行任何操作。
3. 执行顺序固定为：暂存全部改动 → 提交 → 拉取（rebase 方式）→ 推送。
4. 提交信息：
   - 显式提供的 message 原样使用，包含空格、换行、以 `-` 开头等特殊情况都不得被误解析或丢失。
   - 未提供 message 时生成带时间戳的默认提交信息 `nanobot sync @ YYYY-MM-DD HH:MM:SS`，时间使用运行时区。
5. 容错规则：
   - 仅「无改动可提交」不视为失败，流程继续执行后续步骤。
   - 提交步骤的其他失败原因（例如缺少提交者身份配置、提交被本地钩子拒绝）必须按失败处理并报告，不得静默跳过。
   - 其余任一步骤失败即中断后续步骤并报告，不得在失败后继续推送。
6. 超时与交互：每个步骤都需有明确超时上限；任何需要交互输入的场景（凭据、确认、首次连接的主机指纹确认）不得无限等待，超时或无法交互时按失败处理并提示。
7. 不阻塞：命令执行期间不得阻塞 agent 对其他消息的处理；耗时步骤在后台执行，完成后把结果回送到发起会话。
8. 输出要求：
   - 成功：明确的成功标识（`✓ synced`）+ 各步骤的命令回显与输出摘要。
   - 失败：明确的失败标识（`✗ failed (exit N)`）+ 失败步骤 + 可读的原因说明与错误输出。
   - 对常见前置问题给出人能看懂的提示，而不是只回显原始错误：工作区不是 Git 仓库、未配置远程、无推送权限、拉取产生冲突（冲突场景还需说明仓库当前处于什么状态、用户下一步该做什么）。
   - 输出在支持 Markdown 的渠道按 Markdown 呈现；不支持的渠道降级为可读纯文本。任何情况下不得把内部异常信息直接抛给用户。
9. `git` 不可用（未安装或不在 PATH）时返回「Git 未安装」提示，不视为程序错误。
10. 安全边界：
    - 该命令会把工作区内容推送到远程，属于高危操作：只允许已授权用户使用，授权口径与其他高危命令一致；需明确在各渠道下的可用性。
    - 只提交工作区中本应纳入版本管理的内容，遵循工作区自身的忽略规则；不得为了让命令「成功」而放宽或绕过既有忽略配置。
    - 输出中不得泄露凭据、令牌，或远程地址中携带的敏感信息。

### 验收标准

- 有改动与无改动两种情况都能得到明确结果；无改动时不报错。
- 以下失败场景均返回可读提示，且不影响 agent 继续处理后续消息：工作区不是 Git 仓库、未配置远程、无推送权限、拉取冲突。
- 命令执行期间，其他会话的消息仍可被正常处理。
- 提交信息中的空格、换行、`-` 开头文本均按原样进入提交。
- `/git` 与 `/git <message>` 均出现在帮助与用户文档中。

## 需求 3：工作区 Markdown 文件读取命令 `/read`

### 用户故事

作为用户，我希望通过 `/read <filename>` 读取工作区中的 Markdown 文件内容，并由 agent 直接回显，便于快速查看工作区内的文档。

### 功能需求

1. 命令形态：`/read <filename>`；不带参数时返回用法提示。命令需登记为内置命令，并出现在帮助与面向用户的命令文档中。
2. 作用范围：路径相对工作区解析，支持子目录中的文件。**无论工作区限制开关是否开启**，越出工作区的路径（绝对路径、`..` 上跳、符号链接跳转）一律拒绝并提示，不得读取工作区外内容。
3. 文件类型：仅允许 `.md` 后缀（大小写不敏感）；其他类型拒绝并说明只支持 Markdown。
4. 内容规模与编码：
   - 需有输出大小上限，超限时截断并明确提示「已截断」。
   - 无法按文本解码的内容（二进制、非 UTF-8 编码）需给出明确提示，不得导致命令失败崩溃。
5. 错误处理：文件不存在、目标是目录、无读取权限、解码失败、路径越界，均返回明确可读的提示。命令自身不得抛出未处理异常，也不得因此影响 agent 主流程或其他消息的处理。
6. 输出要求：
   - 标题带工作区相对路径。
   - 正文用代码围栏完整包裹，围栏需能容纳文件中已有的代码围栏，避免内容被提前截断或格式串味。
   - 支持 Markdown 的渠道按 Markdown 渲染，不支持的渠道降级为可读纯文本。
7. 能力边界：
   - 本命令为只读，不得修改任何文件，也不得改变既有的文件访问权限边界。
   - 工作区内的 `.md` 文件（含项目指令文件、长期记忆文件）默认可读，因为这些内容对用户本就可见；若后续需要限制，需在本条中显式列出排除项。

### 验收标准

- 以下输入均返回预期结果，且 agent 后续消息处理不受影响：正常读取、不带参数、非 `.md` 文件、文件不存在、目标是目录、路径越界（工作区限制开启与关闭两种情况）、超大文件、无法解码的文件。
- 工作区限制关闭时，工作区外的 `.md` 文件同样被拒绝。
- 文件内含代码围栏时，回显内容完整且格式正确。
- `/read` 出现在帮助与用户文档中。

## 需求 4：项目配置文件命名为 NANOBOT.md

### 用户故事

作为项目方，我希望 agent 的项目级配置文件命名为 `NANOBOT.md` 而非 `AGENTS.md`，以匹配产品命名。

### 功能需求

1. 上下文构建时，项目指令文件来源为 `NANOBOT.md`，不再读取 `AGENTS.md`。
2. 内置模板中对应的项目配置模板文件命名为 `NANOBOT.md`，并在工作区初始化时生成该文件；重复初始化不得覆盖用户已修改的内容。
3. 升级迁移：**本条不适用于本仓库**。本需求是定制项，部署方从一开始就使用 `NANOBOT.md`，不存在「既有工作区有 `AGENTS.md` 而无 `NANOBOT.md`」的升级场景，因此不做自动迁移，也不做重命名提示。若未来出现真实的存量 `AGENTS.md` 工作区，再把本条改回「幂等迁移或明确提示」并按需求落位。
4. 文档与测试用例中的项目配置文件名同步为 `NANOBOT.md`。
5. 范围说明：本需求只约束「agent 的项目级指令文件」命名。仓库自身面向贡献者的开发说明文件不在本需求范围内，核对时无需改动。
6. 保持既有行为：项目指令文件内容与内置模板完全相同（用户未自定义）时，不重复注入上下文。

### 验收标准

- 新建工作区会生成 `NANOBOT.md`，其中自定义的内容会进入 agent 上下文。
- 工作区内的 `AGENTS.md` 不再被读取。
- 不需要迁移能力：核对时无需检查 `AGENTS.md` → `NANOBOT.md` 的迁移或提示（见功能需求第 3 条）。
- 面向用户的文档与测试断言中，项目指令文件名均为 `NANOBOT.md`。

### 上游差异提示

上游默认使用 `AGENTS.md`，本定制与上游命名不一致。每次同步上游后需重新核对以下四处是否被上游改动覆盖：项目指令的读取入口、内置模板文件名、工作区初始化生成逻辑、文档与测试断言。上游若新增 `AGENTS.md` 的迁移/兼容逻辑，本定制不跟随，避免把 `AGENTS.md` 重新变成受支持的文件名。
